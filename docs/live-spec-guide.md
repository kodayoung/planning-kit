# 라이브 기획안 도구 단계별 구축 가이드

프론트 레포는 한 줄도 건드리지 않고, 로컬 프론트 화면 위에 **목업 · 설명 스티커 · 코멘트 · 이력**을 얹는 "기획 도구"를 단계별로 만드는 가이드입니다. 각 단계는 **목표 → Claude Code 지시문 → 확인 체크리스트 → 막히면** 순서로 되어 있어요. 체크리스트를 모두 통과한 뒤 다음 단계로 넘어가세요.

## 전체 그림

```
브라우저 ──▶ 기획 도구(중간 창구, localhost:4000) ──▶ 프론트 개발 서버 ──▶ 실제 백엔드
                 │
                 ├─ 새 기능 API → 목업 응답으로 대신 답함
                 ├─ 화면에 설명 스티커 스크립트를 끼워 넣음
                 └─ 코멘트 → 깃랩 이슈로 저장
```

| 단계 | 결과 | 필수 |
|---|---|---|
| 0 | 프론트 프로젝트 구조 파악 | 필수 |
| 1 | 중간 창구로 화면이 그대로 뜸 | 필수 |
| 2 | 새 기능이 목업으로 동작 | 필수 |
| 3 | 설명 스티커와 스펙 모드 | 필수 |
| 4 | 스티커가 제자리를 찾는지 자동 점검 | 권장 |
| 5 | 깃랩 코멘트 · 멘션 · 알림 | 필수 |
| 6 | 이력 탭과 버전 비교 | 권장 |
| 7 | 동료가 각자 자리에서 실행 | 필수 |
| 8 | 누구나 여는 공유 링크 | 선택 |

## 시작 전 확인할 것

- **사내 보안 정책**: 깃랩 개인 액세스 토큰을 로컬 도구에서 써도 되는지 (5단계)
- **목업 데이터 원칙**: 실제 고객 데이터, 실제 IP · 도메인은 절대 넣지 않고 가상의 값만 사용
- **깃랩 관리자** (8단계를 할 때만): 요금제가 Premium 이상인지, Pages 기능이 켜져 있는지

> 팁: 각 단계를 통과할 때마다 기획 도구 레포에 커밋하고 `step-1`, `step-2`처럼 태그를 달아두면, 문제가 생겼을 때 바로 되돌아갈 수 있어요.

## 0단계. 프론트 프로젝트 구조 파악

**목표**: 이후 단계 지시문에 넣을 정보를 모읍니다. 코드는 수정하지 않아요.

**Claude Code 지시문** (프론트 레포에서 실행)

```
<프론트 레포 경로>의 프론트엔드 프로젝트를 코드 수정 없이 읽기만 해서 아래를 정리해줘.
1. 프레임워크와 버전(React, Vue 등), 개발 서버 종류(Vite, webpack 등)
2. 로컬 개발 서버 실행 명령과 포트
3. API 호출 방식: 상대 경로(/api 등)로 호출하고 개발 서버 프록시가 백엔드로 넘기는지,
   아니면 백엔드 주소로 직접 호출하는지. 관련 설정 파일 위치도 알려줘.
4. 로그인 방식: 쿠키 세션인지, 토큰을 헤더에 넣는지, 토큰을 어디에 저장하는지
5. 화면 라우팅 방식과 주요 화면 경로 목록
6. 필요한 Node 버전
파일은 절대 수정하지 마.
```

**확인**

- [ ] 6개 항목의 답을 메모해 두었다
- [ ] 3번 답이 "상대 경로 + 개발 서버 프록시"인지 "직접 호출"인지 확인했다 (2단계 지시문이 달라짐)

## 1단계. 중간 창구 만들기 (그대로 통과만)

**목표**: `localhost:4000`으로 접속해도 평소 로컬 화면과 똑같이 동작하게 합니다.

**Claude Code 지시문**

```
새 폴더 ~/work/planning-kit 에 "기획 도구" 레포를 만들어줘.
목적은 프론트 레포 코드를 전혀 바꾸지 않고, 로컬 프론트 개발 서버 앞에 중간 창구(프록시)를 세워서
나중에 목업 응답과 설명 스티커를 끼워 넣는 거야.

이번 단계에서는 "그대로 통과"만 구현해.
- Node 기반 프록시 서버, 포트 4000
- 모든 요청을 프론트 개발 서버(http://localhost:<0단계 포트>)로 전달
- 코드 수정 시 자동 새로고침(HMR)용 웹소켓 연결도 전달
- 쿠키와 Set-Cookie가 깨지지 않게 전달. Domain 속성이 있으면 localhost에서 동작하도록 처리
- 설정은 .env (FRONT_URL, PORT). .env.example 제공, .env는 .gitignore
- npm run dev 한 줄로 실행

참고 정보(0단계 결과):
<0단계 답변 붙여넣기>

이 레포에 CLAUDE.md를 만들고 아래 규칙을 넣어줘.
- 프론트 레포(<프론트 레포 경로>)의 파일은 절대 수정하지 않는다. 읽기만 한다.
- 토큰과 비밀번호는 .env에만 두고 커밋하지 않는다.
- 목업 데이터에는 실제 고객 데이터, 실제 IP·도메인을 넣지 않는다. 가상의 값만 쓴다.
- 폴더 구조: proxy/, mocks/, specs/, overlay/, scripts/
```

**확인**

- [ ] 프론트 개발 서버를 평소처럼 켠 뒤 `npm run dev` 실행
- [ ] `http://localhost:4000` 접속 시 로그인이 된다
- [ ] 기존 화면의 데이터가 정상으로 나온다
- [ ] 프론트 코드를 조금 고치면 화면에 자동 반영된다
- [ ] 프론트 레포에서 `git status`를 해도 변경 사항이 없다

**막히면**

- 로그인이 안 되거나 바로 튕김 → 쿠키 전달 문제. 브라우저 개발자도구의 오류와 네트워크 탭 캡처를 Claude Code에 보여주세요.
- 자동 새로고침이 안 됨 → 웹소켓 전달 문제. "HMR 웹소켓이 안 붙어"라고 알려주세요.

## 2단계. 새 기능 목업

**목표**: 백엔드에 아직 없는 새 기능 API만 가짜 응답으로 답하고, 나머지는 실제 백엔드로 보냅니다.

**Claude Code 지시문**

```
기획 도구에 목업 기능을 추가해줘.
- mocks/routes.yaml 에 "메서드 + 경로 → 응답 파일, 상태코드, 지연시간(ms), 사용 여부"를 적는다
- 응답 파일은 mocks/<기능이름>/ 아래 JSON
- 프록시가 API 요청을 받으면 routes.yaml에 있고 사용 중인 것은 목업으로 답하고, 나머지는 그대로 통과
- 모드는 .env의 MOCK_MODE=off | partial | all
  (all은 모든 API를 목업으로. 목업이 없는 API는 콘솔에 경고)
- routes.yaml을 고치면 서버 재시작 없이 반영
- 콘솔에 요청마다 [목업] / [실제] 를 한 줄씩 표시

첫 목업: 프론트 레포의 <기능 브랜치 이름> 브랜치에서 내가 추가한 기능이 호출하는 API를 찾아
목록을 보여주고, 각 API의 가상 응답을 만들어줘. 응답 형식은 프론트 코드가 기대하는 형태에 맞춰줘.
```

0단계 3번에서 **백엔드를 직접 호출**한다고 나왔다면 지시문 끝에 이 문장을 추가하세요.

```
프론트가 백엔드 주소를 직접 호출하는 구조라서 프록시 단계에서는 가로챌 수 없어.
화면에 스크립트를 끼워 넣어 브라우저 안에서(fetch/XHR 또는 서비스 워커) 가로채는 방식으로 구현해줘.
```

**확인**

- [ ] 새 기능이 목업 데이터로 정상 동작한다
- [ ] 기존 기능은 여전히 실제 데이터로 나온다
- [ ] 콘솔에 [목업] / [실제] 구분이 찍힌다
- [ ] `MOCK_MODE=off`로 바꾸면 새 기능이 원래처럼 실패한다 (가로채기가 진짜 동작한다는 증거)
- [ ] 지연시간을 3000으로 바꾸면 로딩 화면이 보인다
- [ ] 상태코드를 500으로 바꾸면 에러 화면이 보인다
- [ ] 프론트 레포 `git status`에 변경 사항이 없다

## 3단계. 설명 스티커와 스펙 모드

**목표**: 화면 위에 번호 스티커를 띄우고, 스펙 모드에서 요소를 누르면 설명 카드가 뜨게 합니다.

**Claude Code 지시문**

```
설명 스티커(오버레이)를 추가해줘. 프론트 코드는 수정하지 않고,
프록시가 HTML 응답에 overlay 스크립트를 끼워 넣는 방식이야.

[스펙 파일] specs/<화면이름>.yaml
- screen, route(화면 경로), title
- elements 목록: id, name, locator, description, behavior(동작), states(상태별 처리), since(버전)
- locator는 Playwright처럼 역할+텍스트로 찾는다. 예: { role: button, name: "내보내기" }
  within(상위 영역)으로 범위를 좁힐 수 있고, 마지막 수단으로 css도 허용

[오버레이 동작]
- 화면 하단 작은 툴바: 사용 / 스펙 모드 전환, 스티커 보이기 on/off
- 사용 모드: 요소 옆에 번호 스티커만 표시. 클릭은 절대 가로채지 않음
- 스펙 모드: 마우스를 올리면 요소에 테두리. 클릭하면 원래 동작은 막고 요소 옆에 설명 카드를 띄움
- 설명 카드는 팝오버 형태. 드래그로 옮기기, 고정하기 가능. 화면 레이아웃을 밀어내는 패널은 쓰지 않음
- 사용 모드에서도 Alt(맥은 Option)+클릭하면 설명 카드만 열림
- 단축키: S 스펙 모드, Esc 사용 모드. 입력창에 커서가 있을 땐 단축키 무시
- 모드를 바꿔도 새로고침하지 않아서 열린 모달 등 화면 상태가 유지됨
- 화면 이동, 스크롤, 모달 열림, 창 크기 변경 시 스티커 위치 자동 갱신
- 오버레이는 Shadow DOM 안에 만들어서 프론트 스타일과 서로 영향 없게
- 현재 경로에 맞는 스펙 파일만 적용
- 스펙 파일을 고치면 새로고침 없이 반영

샘플로 <화면 경로> 화면의 스펙 파일을 만들어줘. 요소 5개 정도, 설명은 내가 채울 수 있게 틀만.
```

**확인**

- [ ] 샘플 화면에 스티커 5개가 올바른 요소 옆에 뜬다
- [ ] 사용 모드에서 버튼을 누르면 원래 동작이 그대로 일어난다
- [ ] 스펙 모드에서 누르면 동작 없이 설명 카드만 뜬다
- [ ] 사용 모드에서 Alt+클릭 시 설명 카드만 뜬다
- [ ] 모달을 연 상태에서 스펙 모드로 바꿔도 모달이 유지되고, 모달 안 요소의 스티커가 보인다
- [ ] 스크롤하거나 창 크기를 바꿔도 스티커가 따라간다
- [ ] 프론트 화면의 글꼴이나 색이 변하지 않았다
- [ ] 입력창에 S를 타이핑해도 모드가 바뀌지 않는다

## 4단계. 스티커 위치 자동 점검

**목표**: 프론트 화면이 바뀌어 스티커가 요소를 못 찾게 됐을 때 바로 알 수 있게 합니다.

**Claude Code 지시문**

```
scripts/check-specs 를 만들어줘.
Playwright로 localhost:4000에 접속해서 스펙 파일의 화면을 차례로 열고,
모든 요소의 locator가 정확히 1개를 찾는지 검사해.
- 결과를 화면별로 OK / 못 찾음 / 여러 개 찾음 으로 표시
- 로그인이 필요하면 .env의 테스트 계정으로 로그인 (계정 정보는 .env에만)
- 모달 안 요소처럼 사전 동작이 필요한 경우, 스펙 파일에 prepare(순서대로 클릭할 요소)를 적을 수 있게 해줘
- npm run check 로 실행
```

**확인**

- [ ] `npm run check` 결과가 모두 OK
- [ ] 스펙 파일의 버튼 이름을 일부러 틀리게 바꾸면 "못 찾음"으로 나온다 (확인 후 원래대로)

> 운영 규칙: 프론트 main이 머지되어 새로 받을 때마다 `npm run check`를 실행하세요. "못 찾음"이 나오면 Claude Code에 "check 결과 보고 locator 고쳐줘"라고 하면 됩니다.

## 5단계. 깃랩 코멘트 · 멘션 · 알림

**먼저 깃랩에서 할 일 (기획자)**

1. 기획 도구 레포를 깃랩에 올리고, 개발자와 QA를 멤버로 초대
2. 라벨 `스펙코멘트` 만들기
3. 화면마다 이슈 만들기 (예: "스펙: 자산 목록"), 이슈 번호를 해당 스펙 파일에 `issue: 12`처럼 적기
4. 개인 액세스 토큰 발급 (권한 `api`) → 기획 도구의 `.env`에만 저장 (사내 정책 확인 후)

**Claude Code 지시문**

```
코멘트 모드를 추가해줘. 코멘트는 깃랩 이슈 코멘트로 저장해.
- 깃랩 API 호출은 브라우저가 아니라 프록시 서버가 한다.
  .env의 GITLAB_URL, GITLAB_TOKEN, GITLAB_PROJECT_ID 사용. 토큰은 브라우저로 절대 내려보내지 않음
- 스펙 파일의 issue 번호에 해당하는 이슈에 코멘트를 남긴다
- 코멘트 첫 줄에 [spec:요소id] [branch:현재 프론트 브랜치 이름] 태그를 자동으로 붙인다
- 툴바에 코멘트 모드 추가 (단축키 C). 요소를 클릭하면 그 요소의 코멘트 목록과 입력창이 카드로 뜬다
- 스펙 모드 설명 카드에도 "코멘트" 탭 추가
- 스티커에 미해결 코멘트 수 표시
- 입력창에서 @ 입력 시 프로젝트 멤버 자동완성, 저장 시 @username 형태로 들어가게
- 답글은 같은 스레드(깃랩 discussion)로
- 해결 버튼은 깃랩 스레드 해결 기능 사용. 우리 깃랩 버전에서 이슈 스레드 해결이 안 되면 대체 방법을 제안해줘
- 카드를 열 때마다 새로 불러와서 깃랩에서 직접 단 답글도 보이게
- 각 코멘트에 "깃랩에서 열기" 링크
```

**확인**

- [ ] 코멘트를 쓰면 깃랩 이슈에 태그와 함께 등록된다
- [ ] 동료를 @멘션하면 동료에게 깃랩 알림 또는 메일이 간다
- [ ] 동료가 깃랩에서 단 답글이 오버레이에 보인다
- [ ] 해결 처리하면 스티커의 미해결 숫자가 줄어든다
- [ ] 브라우저 개발자도구 네트워크 탭 어디에도 토큰이 보이지 않는다

**막히면**

- 멘션 메일이 안 옴 → 동료가 프로젝트 멤버인지, 동료의 깃랩 알림 설정에서 멘션 알림이 켜져 있는지, 사내 깃랩 메일 발송이 설정돼 있는지 확인

## 6단계. 이력 탭과 버전 비교

**목표**: 요소별로 설명이 언제 어떻게 바뀌었는지 보고, 버전 간 변경점을 스티커 색으로 확인합니다.

**Claude Code 지시문**

```
설명 카드에 "이력" 탭을 추가해줘.
- 프록시가 기획 도구 레포의 git 기록에서 해당 요소의 설명이 바뀐 커밋만 골라
  날짜, 작성자, 커밋 메시지, 바뀐 내용(전/후)을 보여줌
- 커밋 메시지에 이슈 번호(#12)나 코멘트 링크가 있으면 클릭 가능한 링크로 표시
- 툴바에 "비교 기준" 선택 추가: 기획 도구 레포의 태그 목록(예: spec-v1) 중 하나를 고르면
  그 이후 신규 / 수정된 요소를 스티커 색으로 구분
```

**운영 규칙**

- 커밋 메시지: `spec(asset-list-03): 내보내기에 CSV 형식 추가 (#12 논의 반영)`
- 기획 확정 시 태그: `spec-v1`, `spec-v2` …

**확인**

- [ ] 설명을 고쳐 커밋하면 이력 탭에 전/후가 나온다
- [ ] 커밋 메시지의 이슈 번호가 링크로 열린다
- [ ] 태그를 달고 설명을 하나 고친 뒤, 비교 기준을 그 태그로 고르면 해당 스티커 색이 바뀐다

## 7단계. 동료가 각자 자리에서 실행

**목표**: 개발자와 QA가 README만 보고 자기 PC에서 띄울 수 있게 합니다.

**Claude Code 지시문**

```
동료 개발자·QA가 자기 자리에서 쓸 수 있게 준비해줘.
- README: 설치, .env 설정(각자 토큰 발급 방법 포함), 실행 방법, 자주 생기는 문제
- npm run setup: 필요한 것 설치와 .env 생성 도우미
- 실행 시 프론트 개발 서버가 안 떠 있으면 친절한 안내 메시지
- 툴바에 현재 프론트 레포에서 체크아웃된 브랜치 이름 표시
```

**확인**

- [ ] 동료 한 명에게 README만 주고, 도움 없이 실행되는지 확인
- [ ] 동료가 프론트 레포에서 기획자 브랜치로 바꾸면 시연 화면과 같은 화면이 뜬다
- [ ] 동료가 남긴 코멘트가 동료 이름으로 깃랩에 등록된다

> 이 방식에서 브랜치 전환은 "각자 프론트 레포에서 브랜치를 바꾸고 다시 보기"입니다. 화면 안 드롭다운 전환은 8단계 공유 링크에서 가능해요.

## 8단계 (선택). 누구나 여는 공유 링크

**목표**: 개발 환경이 없는 사람도 링크로 열어볼 수 있게 합니다.

**먼저 확인**

- 깃랩 요금제 Premium 이상 (브랜치별 Pages 병렬 배포에 필요)
- 사내 깃랩에 Pages 기능이 켜져 있고, 프로젝트 멤버만 볼 수 있게 접근 제한 가능한지
- CI 러너 사용 가능 여부
- 공유 링크는 **모든 API가 목업**이어야 해서, 공유할 화면만 골라 목업을 채우는 품이 듭니다

**Claude Code 지시문**

```
기획 도구 레포에 깃랩 CI를 추가해서 공유 링크를 만들어줘. 프론트 레포는 수정하지 않아.
- 수동 실행 파이프라인. 입력값으로 프론트 브랜치 이름을 받음
- 프론트 레포의 해당 브랜치를 읽기 전용으로 받아서 빌드
- 빌드 결과에 오버레이 스크립트, 스펙, 목업을 끼워 넣음.
  서버가 없으니 목업은 브라우저 안에서(서비스 워커 등) 처리하고, 모든 API를 목업으로
- 로그인 API도 목업으로 처리해서 링크를 열면 바로 화면에 들어오게
- 깃랩 Pages 병렬 배포로 브랜치 이름 경로에 올림. 만료 2주. 태그로 실행하면 만료 없음
- 하위 경로에서도 프론트가 동작하도록 빌드 시 기본 경로 설정
- 공유 링크에는 토큰이 없으니 코멘트 작성은 빼고 "깃랩 이슈에서 보기" 링크만 표시
- 툴바에 배포된 브랜치 목록 드롭다운. 고르면 같은 화면 경로 그대로 이동
```

**확인**

- [ ] 파이프라인 실행 후 링크가 생긴다
- [ ] 프로젝트 멤버가 아닌 계정으로는 열리지 않는다
- [ ] 로그인 없이 화면에 들어가고, 공유할 화면이 모두 목업으로 동작한다
- [ ] 드롭다운으로 다른 브랜치를 고르면 같은 화면으로 이동한다
- [ ] 2주 뒤(또는 만료 시간을 짧게 바꿔 테스트) 링크가 사라지고, 태그 링크는 남아 있다
